# ملخص تنفيذ RBAC متعدد الشركات — TopDent

## ما أُنجز

- إضافة نموذج عضويات وصلاحيات متعدد النطاقات (`platform` / `company` / `self`) مع عضويات نشطة، شركات، أدوار مخصصة، أذونات، سجل تدقيق، اشتراكات، سائقين، تعيينات، وحالات fulfillment منفصلة لكل شركة.
- تحويل ملكية المنتجات وبنود الطلبات القديمة إلى شركات منفصلة لكل تاجر قديم، مع الاحتفاظ بالطلبات والدفاتر المالية وعدم حذف البيانات.
- استبدال سياسات RLS المتعارضة للبيانات الحساسة، وإبطال الكتابة المباشرة للأدوار والعضويات والسائقين والتعيينات وسجلات الحالة والأرصدة وحالات الطلبات.
- إضافة فحوص مشتركة للعضوية والصلاحية ونطاق الشركة في Edge Functions، وحماية مسارات التطبيق، بما فيها فحص منفصل لنطاق المنصة حتى لا تسمح صلاحية شركة بفتح لوحة المنصة.
- إضافة لوحات المنصة والشركة والسائق، وإدارة الفرق والأدوار والتقارير والاشتراكات والتدقيق، وتدفق تعيين/قبول السائق والتحصيل والإبلاغ عن المشكلات.
- إضافة اختيار سرعة التوصيل ونافذة موعد مفضلة عند الدفع. يحافظ المسار الجديد على رسوم الشحن الحالية، ويتحقق الخادم من الموعد والسرعة ضمن معاملة الطلب الأصلية.
- ربط سجل الحالات بصفحة تفاصيل الطلب، وتحويل إلغاء العميل إلى RPC خادمي مُدقّق بدلاً من تحديث مباشر غير مسموح.

## الخدمات الخلفية

- وظائف جديدة: `company-admin`, `driver-api`, `order-admin`, `product-admin`, `role-admin`, `user-admin`.
- ملفات مشتركة: `supabase/functions/_shared/authorization.ts`، وإعدادات Deno في `supabase/functions/deno.json`.
- وظائف معدّلة: `admin-api` و`merchant-api`.

## خريطة مختصرة للأدوار

- **platform_owner**: صلاحيات المنصة الكاملة، بما فيها تفعيل الشركات، من دون صلاحية حذف سجل التدقيق.
- **platform_admin**: صلاحيات المنصة الممنوحة صراحةً فقط؛ لا يحصل على كل شيء تلقائياً.
- **company_admin / company_manager**: صلاحيات محددة ضمن الشركة المرتبطة بالعضوية فقط.
- **company_driver / global_driver**: بيانات وإجراءات التوصيل المسموح بها فقط، مع تحقق أن الطلب معيّن للسائق.
- **publisher**: روابطه وأرباحه وطلبات السحب الخاصة به.
- **customer**: حسابه وطلباته وطلباته المتعلقة بمحفظته؛ التسجيل العام لا يمنح أدوار منصة أو شركة.

## آلية العزل

يختار العميل الشركة من عضوية نشطة فقط؛ ويُمرّر `company_id` إلى استعلامات الشركة، لكن قاعدة البيانات وEdge Function تعيدان التحقق من الصلاحية والنطاق. تعتمد RLS على `has_permission` و`can_access_company`، وتستخدم المسارات المحمية كطبقة تجربة مستخدم لا كبديل للأمان الخادمي. سجلات التغييرات المالية والأمنية وتغييرات الحالة تُكتب عبر RPC/Edge Function وتبقى غير قابلة للتعديل المباشر.

## التحقق المنفّذ

- `npm run check`: **ناجح** (TypeScript للتطبيق، Deno Edge Functions، و6 اختبارات smoke).
- `npm run lint`: **ناجح بلا أخطاء**؛ ظهرت 98 تحذيراً غير حاجباً، أغلبها قواعد lint على استخدامات/متغيرات في قاعدة المشروع.
- تحليل PostgreSQL grammar: **نجح للترحيلات الخمسة**.
- `npm run build:web`: **نجح** بعد آخر تغييرات المسارات. ظهرت تحذيرات غير حاجبة من إعدادات `three` لكنها لم تمنع تصدير الويب.
- اختبارات قبول API وRLS الحية تتطلب مشروع Supabase مرحلياً؛ لا يوجد اتصال قاعدة بيانات مرحلي ضمن هذا التنفيذ، لذلك لم تُطبّق الترحيلات أو تُرسل تغييرات إلى GitHub.

## ملاحظات قبل النشر

- خذ نسخة احتياطية، وطبّق الترحيلات على staging أولاً، ثم نفّذ [مصفوفة اختبارات القبول](../supabase/tests/rbac-acceptance.md).
- يجب تعيين أول `platform_owner` عبر إجراء إداري/SQL مراقب؛ لا يوجد إنشاء مالك عبر التسجيل العام.
- يجب أن يبقى `public.place_order_from_cart(uuid,text)` متاحاً؛ RPC الجديد يستدعيه ويشترط أن يعيد `order_id`.
- لم أستخدم رمز GitHub الظاهر في النص المرفق ولم أرفع المشروع للمستودع. يُستحسن إبطال ذلك الرمز وإصدار بديل إذا كان لا يزال فعالاً.
